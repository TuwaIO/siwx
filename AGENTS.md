# 🤖 Agent Context: Sign-In With X (`@tuwaio/siwx`)

## 1. Project Philosophy & Goal

- **What is this?** A monorepo for **SIWX (Sign-In With X)** — headless, framework-agnostic authentication for EVM and Solana accounts. It implements the [CAIP-122](https://github.com/ChainAgnostic/CAIPs/blob/main/CAIPs/caip-122.md) message format and ships chain signers/verifiers, React bindings and server utilities.
- **Role in TUWA:** Stage 1 of the ecosystem ("Core Auth & Primitives", next to Orbit Utils). Satellite Connect and Pulsar (Stage 2), Quasar (Stage 3), Nova UI Kit (Stage 4) and the TUWA SDK build on it, and SIWX must never depend on them. SIWX itself builds on `@tuwaio/orbit-core` (Orbit Utils, Stage 1) for chain identifiers. Inside the repo, `siwx-core` is the L1 package and `siwx-evm`, `siwx-solana`, `siwx-react`, `siwx-server` are L2 packages; L1/L2 are layers of this project, not of the whole ecosystem.
- **Philosophy:** Headless, backend-agnostic, Sovereign Individual. No framework lock-in, no hosted services, no Wallet-as-a-Service. The server is the source of truth: client state is UI only, nonces are single-use, sessions are `HttpOnly` cookies. Side effects (network calls, storage, cookies) must be explicit and documented.

## 2. Tech Stack (Verified)

- **Core:** TypeScript 6.0.3 (pinned exactly in the root and every `packages/*` `package.json`), Node.js 20+, pnpm v12+ (Workspace).
- **Testing:** `vitest` v5.x (run per package via `pnpm test`); `jsdom` and `@testing-library/react` for `siwx-react`.
- **Web3 (EVM):** `viem` (peer `>=2.18.6`, the first release with stable ERC-6492 verification) and `@wagmi/core` (peer `>=3`) — peer dependencies of `siwx-evm`.
- **Web3 (Solana):** `@solana/kit` (peer `>=6`) and `@wallet-standard/base` (peer `>=1.1.0`, types of the signer target) — peer dependencies of `siwx-solana`. ed25519 verification uses the Web Crypto API (`crypto.subtle`).
- **React:** `react` (peer `>=18`), `zustand` v5 (peer `>=5`) with the `immer` (peer `>=10`) and `persist` middlewares. The verified session is saved to `localStorage` (`siwx-react:session`) and restored after mount.
- **Chain identifiers:** `@tuwaio/orbit-core` (peer `>=0.5`, `devDependencies` `^0.5.0`) in every package: `parseCaip2ChainId`, `parseCaip10AccountId`, `formatCaip10AccountId`, `toCaip2ChainId`, `toEvmChainId` and the Solana chain table behind `getSolanaChainId`. `normalizeSolanaChainId` of `siwx-core` reads that table.
- **Server:** `siwx-server` has `@tuwaio/siwx-core` as a required peer and `@tuwaio/siwx-evm`, `@tuwaio/siwx-solana`, `viem` as optional peers (`peerDependenciesMeta`).
- **Peers between SIWX packages:** plain `>=` ranges with the lowest version the package needs (e.g. `"@tuwaio/siwx-core": ">=0.5"`); `devDependencies` keep `workspace:*`. Never use `workspace:*` in `peerDependencies`: `pnpm publish` turns it into the exact version, so every `siwx-core` release would leave the other published packages asking for the old one (and installs a second `siwx-core`).
- **Frameworks:**
  - `apps/docs`: Next.js v16, Nextra v4, Tailwind CSS v4, `@tuwaio/docs-ui`, Pagefind.
  - `packages/*`: Framework Agnostic, except `siwx-react` (React) and `siwx-server/next` (Next.js App Router shaped, but only uses Web `Request`/`Response`).
- **Docs generation:** TypeDoc 0.28 + `typedoc-plugin-markdown` 4 (config: root `typedoc.json` and `packages/siwx-server/typedoc.json`, local plugins in `apps/docs/typedoc/`).
- **Build/Monorepo:**
  - `tsup`: Bundler for `packages/*` (ESM/CJS/DTS).
  - `release-please` (stable releases of `packages/*` from `main`) and `semantic-release` (`alpha.release.config.js`, prereleases).

### Module Breakdown

- **`siwx-core`**: Builds, parses and validates CAIP-122 messages, enforces verification policies, generates nonces, matches sessions to addresses. Solana chain IDs use the genesis hash of CAIP-30 (`solana:EtWTRABZaYq6iMfeYKouRu166VU2xqa1` for devnet); `normalizeSolanaChainId` maps the Wallet Standard names (`solana:devnet`), `solana:mainnet-beta` and the old testnet ID to it, so policies and session checks treat both forms as one chain. `validateMessage` reads the CAIP-10 address and the CAIP-2 chain ID with the parsers of `@tuwaio/orbit-core`, so an `eip155` or `solana` account must be a valid address of its namespace. `parseMessage` throws `SiwxParseError`; the validators return results. Policy error classes exist but are not thrown by SIWX.
- **`siwx-evm`**: `createEvmSiwxSigner` (wagmi `Config` or viem `WalletClient`), `verifyEip191` (local recovery), `verifyEip1271` (viem `verifyMessage`: EIP-1271 for deployed and ERC-6492 for not yet deployed smart contract wallets, one `eth_call`), `verifyEvmSignature` (EIP-191 with that fallback). `publicClient` is a client or a function of the chain number (`EvmPublicClientSource`); a single client is used only for messages of its own chain. Verifiers never throw.
- **`siwx-solana`**: `createSolanaSiwxSigner` (duck-typed: `@solana/kit` message signers, Wallet Standard `solana:signMessage`, legacy adapters, `useWallet()` of `@solana/wallet-adapter` v1/v3; `messageFormat` `'auto'` | `'message'` | `'offchainMessage'` for `solana:signOffchainMessage`), `verifyEd25519` (Web Crypto; accepts signatures over the message or its version 1 off-chain message envelope, built with `@solana/kit`). No RPC calls.
- **`siwx-react`**: `useSiwx` (`building` → `signing` → `verifying`), `useSiwxSession`, `useSiwxSessionStore` (zustand store; the session is persisted to `localStorage` and restored after mount, never during SSR), duck-typed Satellite Connect helpers. No UI components, no network calls of its own.
- **`siwx-server`**: `verifySiwxPayload` (dynamically imports the optional peers `siwx-evm` / `siwx-solana`), `SiwxSessionStore` / `SiwxNonceStore` contracts and in-memory implementations, sessions that keep how the signature was verified (`verificationMethod`, from `result.method`), cookie helpers, stateless demo tokens and signed demo nonces, `getSiwxServerSession`; JWTs for external auth (`jwt.ts`: `siwxJwtSubject`, `signSiwxJwt`, `verifySiwxJwt`; `jwtKeys.ts`: `generateSiwxJwtKey`, `importSiwxJwtKey`, `siwxJwkThumbprint`, `createSiwxJwks`; ES256/RS256 with Web Crypto, `kid` = RFC 7638 thumbprint); `./next` exports `createSiwxApiHandler` (durable, with the optional `jwt` option for `GET /token` and `GET /jwks`) and `createStatelessDemoSiwxHandler` (demo, no JWT routes). Both handlers accept only nonces issued by their `/nonce` route, once.

### Documentation Model

- The docs site has an **Introduction** (hand-written), a **Packages** section (generated) and a sidebar link to the TUWA guides at `docs.tuwa.io/guides`.
- Each package page at `/packages/<package>` is the package `README.md` followed by the generated list of exports; every export has its own page generated from its JSDoc.
- `siwx-server` has two modules, named with `@module` tags in the entry files: `server` (`@tuwaio/siwx-server`, `/packages/siwx-server/server`) and `next` (`@tuwaio/siwx-server/next`, `/packages/siwx-server/next`). Never name a module `index`: Nextra cannot serve a folder with that name. The sidebar labels them with their import paths through `apps/docs/typedoc/meta/siwx-server/**/_meta.tsx`, which `pnpm docs:gen` copies over the generated tree; add a folder there for every new multi-entry package.
- `typedoc.json` maps the `@tuwaio/siwx-*` imports to their sources (`compilerOptions.paths`), so cross-package links point to the defining package and the output does not depend on `dist`. `excludeExternals` hides members inherited from external types (e.g. `Error`).
- This layout (introduced by Orbit Utils) is the template for the other TUWA documentation sites (Pulsar, Satellite Connect, Nova UI Kit, SDK). Keep it consistent.

## 4. Coding Standards (STRICT)

- **Language:** English ONLY (Code, Comments, Commits, Docs).
- **Style:** Functional programming. Pure functions preferred.
- **Types:** Strict TypeScript. **NO `any`**. Usage of `ts-expect-error` must be justified.
- **Comments:** JSDoc required for **all** exported functions, classes, types and constants in `packages/*/src`.
  - Must explain _inputs_ (`@param`), _outputs_ (`@returns`), _errors_ (`@throws`) and _side effects_.
  - JSDoc is published verbatim as the docs reference page of the export. Keep it accurate and complete.
  - Use only standard TSDoc tags (no `@name`, no `@fileoverview`; use `@file` for file headers); `@param` names must match the real parameters (use `params.<field>` for destructured objects).
  - Use `{@link X}` only for symbols exported by the same package. For other packages, and inside comments of `siwx-core` types that `siwx-react` or `siwx-server` re-export, write the name as code with its package (e.g. `` `buildMessage` from `@tuwaio/siwx-core` ``).
  - Mark exports that are not part of the public API with `@internal`; they are excluded from the reference.
- **Package READMEs** (`packages/*/README.md`) are both the npm page and the docs overview page:
  - Use **absolute URLs** for links (e.g. the LICENSE link). Relative link targets are copied into the generated docs and break Nextra.
  - Do **not** hand-write lists of exports or API signatures; the generated reference lists them.
  - Every code example must compile against the current source.
- **Naming:**
  - Files: `camelCase.ts` (utils, hooks, stores), `PascalCase.tsx` (components).
  - Variables/Functions: `camelCase`.
  - Types/Interfaces: `PascalCase`.

## 5. Key Workflows

- **Build:** `pnpm build` (Builds all packages via `tsup`).
- **Test:** `pnpm test` (Runs `vitest run` across all packages).
- **Lint/Format:** `pnpm lint` (ESLint) / `pnpm format` (Prettier).
- **Docs reference:** `pnpm docs:gen` (TypeDoc → `apps/docs/src/content/packages`; also runs in the pre-commit hook).
- **Docs site:** `pnpm --filter @tuwaio/siwx-docs dev`.
- **Clean:** `pnpm clean` (Nukes `node_modules` and `dist` dirs).

## 6. AI Agent Behavior (Mandatory)

- **Post-Work Routine:** After generating or modifying code, you **MUST** run `pnpm lint --fix` and `pnpm format` to ensure code quality.
- **Docs Routine:** After changing exports, JSDoc or a package README, run `pnpm docs:gen` and check that it reports no warnings. Run it again after `pnpm format`, because Prettier reformats README code blocks. Never edit files under `apps/docs/src/content/packages` directly.
- **Dependency Rule:** Never install new packages without explicit user permission.
- **Hallucination Check:**
  - Do **NOT** import `ethers.js` (We use `viem`).
  - Do **NOT** import `gill` (Eradicated; we use `@solana/kit` and Web Crypto).
  - Do **NOT** import legacy `@solana/web3.js` methods.
  - Do **NOT** compare Solana chain IDs as plain strings or build them as `solana:${cluster}`: sessions signed before the switch carry `solana:devnet`, new ones the genesis-hash ID. Use `normalizeSolanaChainId` / `isChainIdAllowed`.
  - Do **NOT** split or build CAIP-2 / CAIP-10 strings by hand (`split(':')`, template strings) or keep another Solana chain table: use the helpers of `@tuwaio/orbit-core`, the one source of chain identifiers in TUWA.
  - Do **NOT** assume Starknet or Cosmos support exists (v1 is EVM + Solana only).
  - Do **NOT** treat the persisted `siwx-react` session as proof of identity: it is UI state; servers verify the cookie.
  - Do **NOT** add UI components to any package (`siwx-react` ships only hooks and a store).
  - Do **NOT** couple `siwx-server` or any package to Quasar. It is a consumer, not a dependency.
  - Do **NOT** check a smart contract wallet signature on a client of another chain or call `isValidSignature` by hand: pass a client per chain (`publicClient` as a function) and let `verifyEip1271` (viem `verifyMessage`, ERC-6492 included) decide.
  - Do **NOT** add `jose` or another JWT library: `siwx-server` signs and verifies JWTs with Web Crypto (`jwt.ts`, `jwtKeys.ts`).
  - Do **NOT** build a JWT `sub` by hand: use `siwxJwtSubject`. It drops the chain only when a key controls the address on every chain (`eip191`, Solana) and keeps it for smart contract wallets (`eip1271`, `erc6492`) and for EVM sessions without `verificationMethod`. Create sessions with `toSession(result.data, result.method)`. Do **NOT** store JWTs in the `siwx-react` store: they are fetched fresh from `/token`.
  - Do **NOT** use `typedoc-plugin-react` (it files functions under `components/` and breaks reference links).
  - Do **NOT** loosen the domain checks: `parseMessage` and `validateMessage` accept only an RFC 3986 authority (`AUTHORITY_REGEX` in `validateMessage.ts`), so bytes that are not a sign-in message never become a domain. `buildMessage` throws on missing required fields and line breaks; keep format checks in `validateMessage`, because tests and servers build invalid messages on purpose.
  - Do **NOT** add a request field or server option for Solana off-chain message signatures: the version 1 envelope is fully determined by the text and the address, so `verifyEd25519` tries the plain message, then the envelope. Do **NOT** accept off-chain message versions other than 1, or envelopes whose required signers are not exactly the message address.
